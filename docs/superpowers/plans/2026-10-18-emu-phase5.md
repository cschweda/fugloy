# Emu Phase 5 (Disk Controller and Disk Images) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The Model III runs from disk: `m.fdc` mounts JV1, JV3, and DMK images, the WD1793 behaves as its datasheet says, a DOS boots from a disk image, and a disk-based game runs (emu spec §11 phase 5), with the MCP server's `load` taking disk images too.

**Architecture:** `packages/emu` already carries upstream's `devices/fdc-wd1793.js` and `devices/disk-image.js` (JV1/JV3/DMK parsing, a DMK track writer) wired into `TRS80System` (ports `F0–F4`, NMI from INTRQ through port `E4`). This phase puts them behind the `Machine` facade, audits the controller against the datasheet with synthetic images, closes the NMI items the spec assigns here, adds DMK export, and proves booting on the real images in the gitignored `fixtures/real/`.

**Tech Stack:** plain JavaScript ESM (emu, mcp), Vitest.

**Spec:** `docs/fugloy-emu-spec.md` §3 (`m.fdc.mount/unmount`, `m.load.dsk`), §4 (the NMI held off after a lone prefix, deferred here), §5 (FDC row: WD1793 at ports `F0–F3`, drive select and density `F4`, NMI status `E4`), §6 (`.DSK`/JV1/JV3/DMK: read all three, write DMK only), §7 (snapshots exact: the NMI edge latch), §10 ("Boot TRSDOS 1.3 from a DMK image"), §11 row 5; `docs/fugloy-mcp-spec.md` §5 `load`.

## Global Constraints

- emu: plain JS ESM, no DOM, no Node APIs, deterministic (no wall clock), no runtime dependencies; `test/no-dom.test.js` passes.
- Debugging off must not slow `Machine`: Sea Dragon stays ≥ 20× real time with no disk mounted (measure; report the number).
- Disk images, DOSes, and copyrighted programs are never committed: tests that need them read `fixtures/real/` and skip without it; every behaviour has a synthetic-image test that runs in CI (images built by test writers, like `fixtures/synthetic`).
- WD1793 behaviour is cited to the datasheet (Western Digital FD179X-02 data sheet) or the Model III Technical Reference Manual by section or page in a comment where the code decides it; anything not verified is marked unverified in spec §5.
- Commit messages: imperative, one line, prefix `e5:`. No `Co-Authored-By` or any AI trailer.
- Keep `docs/fugloy-emu-spec.md`, `docs/fugloy-mcp-spec.md`, `CLAUDE.md`, `CHANGELOG.md` (detailed), the emu and MCP READMEs, and the root README current in the task that changes behaviour they describe.

## Rulings made while planning

1. **Done-criterion evidence.** The local disk images are Eliminator and Rear Guard dual-boot DMKs and Scarfman (DSK). If no TRSDOS 1.3 image is present, "a DOS boots" is proven by whatever DOS the dual-boot DMK carries reaching its prompt or menu, and "a disk-based game runs" by a game reaching its title from disk; spec §10's TRSDOS 1.3 row stays open until such an image is added (record it).
2. **API.** `m.fdc.mount(drive, bytes | DiskImage, { writeProtect? })` returns `{ drive, container: 'jv1' | 'jv3' | 'dmk', tracks, sides, sectorsPerTrack?, writeProtected }`; `m.fdc.unmount(drive)`; `m.fdc.drives` (an array of the four drives' mount info or null); `m.fdc.export(drive)` returns DMK bytes (spec §6: write DMK only). `m.load.dsk(bytes, { drive = 0, boot = true })` mounts and, with `boot`, resets so the ROM boots from drive 0; its manifest is `{ format: 'dsk', container, drive, boot, blocks: [] }` (nothing has landed at mount time).
3. **NMI.** The edge latch (`_nmiWasPending`) joins the serialized state (snapshots exact while INTRQ is active), and an NMI after a lone `DD`/`FD` prefix is held off as a maskable interrupt is (spec §4's open item), each with a test.
4. **MCP `load`** detects a disk image by content (DMK header, JV3 header table, JV1 by size/geometry as `disk-image.js` does) and mounts it in drive 0 and boots; its manifest names the container and geometry.

## Review Focus

1. Mounting a file that is not a disk image must refuse with a sentence, not mount garbage that the ROM then reads (Task 1 test `refuses a non-image`).
2. A write to a write-protected disk must fail as the WD1793 reports it (status bit 6), not change the image (Task 2 test).
3. Reset with no disk mounted must still boot to cassette BASIC as before (Task 1 test `no disk, same boot`), and the phase 2/3 determinism and benchmark tests must hold.
4. A snapshot taken while a sector read is in flight must restore to an identical continuation (Task 2 test `snapshot mid-command`).
5. Exporting a disk the program wrote to must round-trip through `mount` byte-identically in sector data (Task 3 test).

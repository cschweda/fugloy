# Emu Phase 2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the Model III devices and the `.CMD`, `.BAS` and `.CAS` loaders behind the spec's `Machine` API, so that three real programs run in `@fugloy/emu` to a recognizable screen.

**Architecture:** A new `Machine` class (`packages/emu/src/machine/machine.js`) is the spec §3 facade. It wraps the existing `TRS80System` instead of replacing it: `TRS80System`, its devices, and the fast loaders stay as they are, and their tests keep passing. `Machine` adds what phase 2 lacks:

- instruction stepping and `run` with reasons;
- a `video` readout;
- a cycle-stamped keyboard queue and a ROM keyboard-scan hook;
- a sound-event ring buffer;
- `load.cmd`, `load.bas` and `load.cas`, each returning a manifest.

**Tech Stack:** Plain JavaScript ESM (no TypeScript in `packages/emu`), Vitest, Node 22.

**Spec:** `docs/fugloy-emu-spec.md`: §2 (design principles), §3 (public API), §5 (Model III), §6 (loaders), §10 (testing), §11 phase 2 ("Three real programs run to a recognizable screen").

## Global Constraints

- **Zero DOM, deterministic.** No `window`, `document`, wall-clock time, `Math.random`, timers, `console`, or `process` in `packages/emu/src`. All timing is in T-states (`cpu.cycles`). `test/platform-free.test.js` and `test/no-dom.test.js` must stay green and must cover every new file.
- **Plain JS ESM.** Add JSDoc types for public methods. No runtime dependencies. File I/O happens only in callers and tests.
- **ROMs are never committed or bundled.** Tests that need one call `configuredRom('model3')` from `test/rom.js` and use `describe.skipIf(rom === null)` with `ROM_TEST_TIMEOUT`. CI has no ROM, so everything that can be tested without one must be.
- **Existing behaviour is kept.**
  - `TRS80System`, `parseCmd`, `parseCas`, `fastLoadCmd`, `fastLoadBasic`, `fastLoadSystem`, `serializeState` and `restoreState` keep their signatures and behaviour, and every existing emu test passes unchanged.
  - `apps/web/test/emulator-run.test.ts` keeps passing.
- **Docs.** Addresses print `$3C00` in prose. Update the spec in the same change when a value in §5 or §6 is verified, corrected or superseded (CLAUDE.md: "Keep the plan current").
- **Commits.** Imperative and one line, prefix `e2:` (emu phase 2), with no AI co-author trailer.
- **Copyright.** Only public-domain programs from `examples/` and synthetic fixtures are committed.

## Review Focus

1. **Keyboard hook and input timing.** A queued key must be seen by the ROM exactly once, whether the program reads the matrix directly (games) or calls `$002B`/`$0049` (BASIC). Typing "AB" must never produce "A", "AAB" or "BA". *Test:* Task 4, `type-once` cases on the matrix path and the hook path.
2. **Determinism across a script.** The same sequence of loads, keys and runs on two fresh `Machine`s must end in byte-identical `serializeState` output, and so must the sound events. *Test:* Task 7, `same-script-twice`.
3. **A `.BAS` file that is neither tokenized nor clean ASCII.** Examples are a file with a stray NUL, a file that ends without the `00 00` terminator, and a file that is CR-LF ASCII. Each must load the way a person would expect or fail with a clear error, never write half a program and report success. *Test:* Task 5, `bas-edge` cases.
4. **Sound ring overflow.** A long session must keep only the newest events, with an `overflowed` count and nothing silently dropped from the middle, and `events(since)` must stay correct across the wrap. *Test:* Task 3, `ring-wrap`.
5. **Loading over a running program.** `load.cmd` on a `Machine` that is mid-run or halted must leave the machine runnable at the entry, with no interrupt pending from the old program's state, as the existing `fastLoadCmd` contract already does. *Test:* Task 6, `load-over-running`.

### Task 1: The `Machine` facade: construction, stepping, running, state access

**Files:**
- Create: `packages/emu/src/machine/machine.js`
- Modify: `packages/emu/src/index.js` (export `Machine`, `ROM_HASHES`)
- Test: `packages/emu/test/unit/machine.test.js` (synthetic ROM, no real ROM needed), `packages/emu/test/integration/machine-boot.test.js` (real ROM, skipped without one)

**Interfaces:**
- Produces:
  ```js
  export class Machine {
    /** @param {{ model?: 3, ram?: 48, roms: { level2: Uint8Array }, log?: (s: string) => void }} opts */
    constructor(opts)
    system      // the wrapped TRS80System (escape hatch; documented as such)
    rom         // { bytes: number, sha256: string, recognized: string | null }
    reset()
    /** Execute n whole instructions; returns { cycles: number, halted: boolean } */
    step(n = 1)
    /** Run until a reason; returns { reason: 'cycles' | 'halt' | 'predicate', cycles: number } */
    run({ cycles, until })   // until: 'halt' | ((m: Machine) => boolean); checked at instruction boundaries
    get cycles()             // total T-states since reset
    cpu: { get regs(), get flags() }   // regs: { a,f,b,c,d,e,h,l,a2,f2,b2,c2,d2,e2,h2,l2,ix,iy,sp,pc,i,r,iff1,iff2,im }; flags: { s,z,h,pv,n,c } booleans
    mem: { read(addr, len): Uint8Array /* copy */, write(addr, bytes), get ram(): Uint8Array /* live 48K view */ }
    io:  { in(port): number, out(port, value) }
  }
  export const ROM_HASHES  // { [sha256: string]: string }  known Model III ROM images, e.g. 'model3-rev-?'
  ```
- Rules:
  - `model` other than 3, or `ram` other than 48, throws `"phase 2 builds the Model III with 48K; …"`. The spec lists other values for later phases.
  - The 30 Hz RTC interrupt fires on the same T-state schedule as `TRS80System.runTStates` (every `RTC_INTERVAL_TSTATES`). `step` and `run` must keep that schedule exactly, so share the scheduling code instead of duplicating it. Refactor it inside `TRS80System` into one method both call; `runTStates` keeps its behaviour.
  - `rom.sha256` is computed with an in-package SHA-256 (no Node `crypto`). `@fugloy/disasm` has `sha256Hex`, but emu must not depend on disasm, so copy the small implementation or write one, with a test vector.
  - `ROM_HASHES` holds the hash of the ROM in the user's `fugloy.mcp.json` once the implementer has computed it locally, labelled by what `configuredRom` points at. Hashes are facts, not copyrighted bytes. Also add any further Model III revision hashes that can be cited, with a comment naming the source.

  - `step(3)` executes exactly 3 instructions, and `cycles` equals the sum of their T-states from `@fugloy/z80`.
  - `run({ cycles: 1000 })` returns reason `'cycles'` with `cycles >= 1000`, overshooting by less than one instruction.
  - `run({ until: 'halt' })` on a program ending in `HALT` returns `'halt'`.
  - `run({ until: m => m.cpu.regs.a === 5 })` returns `'predicate'`.
  - `regs` and `flags` reflect a known state.
  - `mem.read` returns a copy, so mutating it does not change memory, and `mem.write` to RAM is read back.
  - `io.out(0xEC, 4)` sets 32-column mode on the wrapped system.
  - The RTC fires at the same cycle under `step` as under `run`, and as `TRS80System.runTStates` does.
  - Bad `model` and `ram` values throw.
  - The SHA-256 test vector is correct.

  Integration (real ROM): `new Machine({ roms: { level2: rom } })`, then `run` until the screen shows `Cass?`, as `boot.test.js` does through the system, and `rom.recognized` is not null.

### Task 4: Keyboard queue and the ROM keyboard-scan hook

**Files:**
- Create: `packages/emu/src/devices/key-queue.js`
- Modify: `packages/emu/src/machine/machine.js` (`m.keyboard`; drain the queue in `step` and `run`; the hook)
- Test: `packages/emu/test/unit/key-queue.test.js`, `packages/emu/test/integration/keyboard.test.js` (real ROM)

**Interfaces:**
- Produces:
  ```js
  m.keyboard.press(key)          // key: a character ('A', '1', ' ') or a name: 'ENTER','CLEAR','BREAK','UP','DOWN','LEFT','RIGHT','SHIFT','SPACE'
  m.keyboard.release(key)
  m.keyboard.type(str, { cps = 10, mode = 'matrix' })   // queue: each char held for a cycle-timed window, then released
  m.keyboard.feed(str)           // queue chars for the ROM keyboard-scan hook (mode 'hook'); '\n' = ENTER
  m.keyboard.pending             // number of queued events not yet delivered
  ```
- Rules:
  - **Matrix mode.** Queue events carry cycle timestamps computed from `cps` at the CPU clock (`CPU_CLOCK_HZ`). The queue is drained at instruction boundaries in `step` and `run`, pressing and releasing through the existing `KeyboardMatrix`, with key-up gaps so a repeated letter registers twice. Shifted characters press SHIFT as well, using `KeyboardMatrix`'s character map.
  - **Hook mode** (spec §6), to verify against the Model III ROM listing and record in spec §6:
    - When the PC reaches `$002B` (scan: returns the key in A, or 0) and the feed buffer is not empty, the machine sets A to the next character and returns as the routine would (pop the PC; clear the Z flag for a key).
    - At `$0049` (wait for a key), it does the same.
    - When the buffer is empty, it does not intercept and the ROM runs normally.
    - Each character is delivered exactly once.
  - **Programs** that scan the matrix directly ignore hook mode. That is the reason both modes exist.
  - `TRS80System.typeText` stays as it is.

- [ ] **Step 1: Failing tests:**
  - Unit, synthetic: queue timing (`type('AB',{cps:10})` presses A at cycle 0, releases it before pressing B, and B starts about `CPU_CLOCK_HZ/10` later).
  - Unit: `pending` counts down.
  - Unit: names map to the right matrix bits.
  - Integration (real ROM), at the BASIC prompt:
    - `type-once` matrix: `type('PRINT 12+30\n')` then run → the screen shows `42` once.
    - `type-once` hook: `feed('PRINT "AB"\n')` → the screen shows `AB`, not `AAB` or `BA`.
    - A repeated letter (`PRINT "AA"`) types correctly in both modes.
- [ ] **Step 2: Run**; expect FAIL. **Step 3: Implement.** **Step 4: Run**; expect PASS.

### Task 5: `.BAS` loader

**Files:**
- Create: `packages/emu/src/loaders/bas.js`
- Modify: `packages/emu/src/machine/machine.js` (`m.load.bas`), `packages/emu/src/index.js` (export `parseBas`)
- Test: `packages/emu/test/unit/bas.test.js` (synthetic `.bas` from `fixtures/synthetic/bas/` plus inline bytes), `packages/emu/test/integration/bas-load.test.js` (real ROM)

**Interfaces:**
- Produces:
  ```js
  export function parseBas(bytes)  // → { kind: 'tokenized', lines: [{ lineNo, tokens: Uint8Array }] } | { kind: 'ascii', text: string }
  m.load.bas(bytes)                // tokenized: writes the program at TXTTAB, fixes pointers, returns manifest
                                   // ascii: feeds the text through the keyboard hook (Task 4), returns manifest
  // manifest: { format: 'bas', kind: 'tokenized'|'ascii', start: number, end: number|null, blocks: [{ addr, len, why }] }
  ```
- Rules:
  - **Detection** follows the spec: a first byte of `$FF` means tokenized. Otherwise the file is ASCII only if every byte is printable or CR/LF/TAB.
  - **Tokenized** follows the CLAUDE.md reference facts: each line is a 2-byte next pointer, a 2-byte line number, the body, then `00`, and two zero bytes end the program. Next pointers are rebuilt for the load address rather than trusted.
  - **Writing** reuses the logic of `fastLoadBasic` (TXTTAB from `$40A4`, then `$40F9`/`$40FB`/`$40FD`). Factor out a shared writer; don't duplicate it.
  - **ASCII** goes through `m.keyboard.feed` with each line ending in ENTER. `end` is null because it isn't known until BASIC has read the lines.
  - **Errors.** A truncated tokenized file (no final `00 00`, or a line pointer past the end) throws `"truncated .BAS: …"` before writing anything. A NUL in an ASCII file throws `"not a .BAS file: …"`. CR-LF is normalized.

- [ ] **Step 1: Failing tests:**

    - `bas-edge`: a truncated file, a NUL in ASCII, and CR-LF ASCII.
    - The manifest is correct for a tokenized program.
  - Integration (real ROM, at the BASIC prompt):
    - A tokenized synthetic program loaded, then `RUN` typed, shows its expected output.
    - An ASCII program (`10 PRINT "HELLO"` / `20 END`) fed, then `RUN`, shows `HELLO`.
    - `LIST` shows the lines.

- Produces:
  ```js

                      //   CLOAD / SYSTEM loader reads it; the caller types the command. → { format:'cas', kind, name, entry?, blocks, baud, via }
  ```

  - Spec §6 lists `.CMD` records `07` (patch) and `10/1F`. Check whether `parseCmd` handles `07`. If it doesn't, add it, citing the TRSDOS load-module format, and update spec §6 to the verified list.
